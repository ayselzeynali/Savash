# راه‌اندازی پرداخت واقعی TABRIZ WORLD

این سند نقشه پیاده‌سازی امن پنج درگاه انتخاب‌شده است. گزینه‌های داخل صفحه فعلاً فقط انتخاب‌گر رابط کاربری هستند؛ تا زمانی که پذیرندگی، سرور و تأیید تراکنش پیاده‌سازی نشود، هیچ پولی دریافت نمی‌شود.

## درگاه‌ها

| شناسه داخلی | بانک / ارائه‌دهنده |
|---|---|
| `behpardakht` | بانک ملت – به‌پرداخت ملت |
| `sadad` | بانک ملی – سداد |
| `sep` | بانک سامان – پرداخت الکترونیک سامان |
| `sepehr` | بانک صادرات – پرداخت الکترونیک سپهر |
| `pasargad` | بانک پاسارگاد – پرداخت الکترونیک پاسارگاد |

## معماری لازم

1. مرورگر فقط سفارش، شناسه کالا، تعداد و درگاه انتخابی را به API امن ارسال می‌کند.
2. سرور قیمت و موجودی را از پایگاه داده خودش می‌خواند؛ مبلغ ارسالی مرورگر قابل اعتماد نیست.
3. سرور یک سفارش با وضعیت `pending` می‌سازد و با آداپتور همان PSP درخواست پرداخت ایجاد می‌کند.
4. مرورگر به آدرس پرداخت رسمی PSP هدایت می‌شود؛ شماره کارت، CVV2، تاریخ انقضا و رمز پویا هرگز در TABRIZ WORLD دریافت یا ذخیره نمی‌شوند.
5. PSP به آدرس بازگشت HTTPS سرور برمی‌گردد. سرور باید نتیجه را با API استعلام/تأیید رسمی همان PSP بررسی کند.
6. فقط پس از تأیید سرور، سفارش به `paid` تغییر می‌کند. callback تکراری باید idempotent باشد و شناسه تراکنش یکتا ذخیره شود.

## قرارداد پیشنهادی API

### ایجاد پرداخت

`POST /api/payments`

نمونه درخواست:

```json
{
  "orderId": "server-created-order-id",
  "gateway": "behpardakht"
}
```

نمونه پاسخ موفق:

```json
{
  "paymentId": "server-payment-id",
  "redirectUrl": "https://official-psp-payment-url"
}
```

سرور باید مالکیت سفارش، وضعیت آن، قیمت نهایی، فروشنده و امکان ارسال را بررسی کند. `redirectUrl` فقط باید از پاسخ معتبر PSP دریافت شود، نه از ورودی کاربر.

### بازگشت درگاه

`GET/POST /api/payments/callback/:gateway`

این مسیر باید امضای/پارامترهای بازگشت را طبق مستندات رسمی PSP بررسی کند و سپس تراکنش را از خود PSP استعلام کند. صرفاً رسیدن کاربر به صفحه بازگشت به معنی پرداخت موفق نیست.

### وضعیت سفارش

`GET /api/orders/:orderId/payment-status`

فقط وضعیت تأییدشده توسط سرور را برگرداند.

## متغیرهای محیطی سرور

برای هر PSP فقط پس از دریافت مشخصات پذیرندگی رسمی، متغیرهای محرمانه متناظر تعریف شوند. نام‌های زیر نمونه‌اند و باید با مستندات رسمی هر PSP تطبیق داده شوند:

- `BEHPARDAKHT_TERMINAL_ID`, `BEHPARDAKHT_USERNAME`, `BEHPARDAKHT_PASSWORD`
- `SADAD_MERCHANT_ID`, `SADAD_TERMINAL_ID`, `SADAD_KEY`
- `SEP_TERMINAL_ID`, `SEP_MERCHANT_ID`
- `SEPEHR_TERMINAL_ID`, `SEPEHR_MERCHANT_ID`, `SEPEHR_KEY`
- `PASARGAD_MERCHANT_ID`, `PASARGAD_TERMINAL_ID`, `PASARGAD_PRIVATE_KEY`

این فهرست نام‌های پیشنهادی برای مدیریت secrets است، نه تضمین نام یا ساختار واقعی پارامترهای API. قبل از کدنویسی هر آداپتور باید مستندات فنی و قرارداد همان پذیرنده بررسی شود.

## امنیت و عملیات

- هیچ کلید، رمز، توکن یا کلید خصوصی در HTML، JavaScript مرورگر، مخزن Git یا فایل عمومی قرار نگیرد.
- فقط HTTPS؛ اعتبارسنجی سمت سرور؛ محدودیت نرخ؛ ثبت رخداد بدون ذخیره داده حساس.
- مبلغ به ریال/واحد مورد انتظار PSP با تبدیل صریح و تست‌شده ارسال شود؛ تومان و ریال با هم اشتباه نشوند.
- سفارش و تراکنش با شناسه یکتا، وضعیت‌های مشخص، زمان انقضا و idempotency نگهداری شوند.
- بازپرداخت، لغو، مغایرت و تطبیق روزانه تراکنش‌ها طراحی شوند.
- در بازار چندفروشنده‌ای، تسویه سهم فروشندگان و احراز هویت/مدارک پذیرندگی باید با PSP و الزامات حقوقی هماهنگ شود؛ پرداخت به یک حساب شخصی و تقسیم دستی راهکار امن و مقیاس‌پذیر نیست.

## اطلاعاتی که برای فعال‌سازی واقعی لازم است

برای هر درگاهی که می‌خواهید فعال شود:
- قرارداد/پذیرندگی و شناسه ترمینال رسمی
- مستندات فنی نسخه‌ای که به پذیرنده شما داده شده
- دامنه HTTPS و آدرس callback تأییدشده
- حساب تسویه متعلق به پذیرنده واجد شرایط

تا دریافت این موارد، دکمه پرداخت باید غیرفعال بماند و رابط کاربری نباید ادعا کند پرداخت واقعی انجام می‌دهد.
